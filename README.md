# Телескоп (max_bot)

## Назначение решения

Телескоп — планировщик учебных задач для первокурсников в MAX, который помогает организовать дедлайны и отслеживать собственное состояние. Продукт объединяет чат-бот, мини-приложение и HTTP API: бот принимает команды и отправляет напоминания, а приложение позволяет работать с задачами, настроением, заметками и групповым режимом.

**Статус: проект развёрнут и работает.**

## Возможности

- Создание, редактирование и выполнение задач с предметом, сроком и приоритетом.
- Мини-приложение MAX на React и TypeScript.
- Go HTTP API с авторизацией по `initData` MAX.
- SQLite для локальной разработки и Turso для общей постоянной базы.
- Напоминания из бота и через Vercel Cron.
- Распознавание голосовых сообщений через Yandex SpeechKit при включённой настройке.

## Состав и архитектура решения

Пользователь открывает mini-app через MAX. Mini-app отправляет запросы Go API с заголовком `X-Max-Init-Data`; API валидирует пользователя и читает/изменяет общее хранилище. Бот использует тот же `Store` для задач и напоминаний. В production serverless API обслуживает Vercel, данные сохраняются в Turso при наличии credentials; локально API и бот используют общую SQLite-базу в Docker volume.

| Путь | Назначение |
| --- | --- |
| `cmd/bot` | Бот MAX с long polling и обработчиком напоминаний |
| `cmd/server` | Локальный HTTP API на порту `8080` |
| `cmd/tokencheck` | Проверка токена бота через MAX API |
| `pkg/bot` | Обработчики, диалоги и клиент бота |
| `pkg/httpapi` | REST API мини-приложения |
| `pkg/storage` | SQLite/Turso-хранилище и модели |
| `pkg/reminders` | Планирование и отправка напоминаний |
| `api` | Serverless-функции Vercel: API, webhook и cron |
| `frontend` | React-приложение и его интерфейс |
| `docs` | Дополнительная документация проекта |

## Требования

- Docker Desktop с Docker Compose v2.
- Go `1.25` и Node.js `24` нужны только для запуска команд разработки вне Docker.
- Действующий `MAX_BOT_TOKEN` нужен для запуска бота и проверки MAX `initData`.
- Для проверки внутри MAX нужны публичный HTTPS URL и подключение mini-app к выданному боту организаторами.

## Быстрый запуск

Создайте локальный файл настроек из шаблона:

```powershell
Copy-Item .env.example .env
```

Откройте `.env` и задайте `MAX_BOT_TOKEN`. Без токена контейнеры `api` и `web` запустятся, но `bot` не сможет подключиться к MAX. Из корня проекта одной командой запустите все локальные компоненты:

```powershell
docker compose up --build
```

После сборки откройте `http://localhost:5173/?demo=1`. Это demo-режим с синтетическими задачами и состоянием в браузерном `localStorage`; он не обращается к API и не авторизует в MAX. Локальный API доступен на `http://localhost:8080`. Для проверки авторизации и постоянного API-сценария откройте опубликованное приложение через MAX.

Сервисы `api` и `bot` используют одну SQLite-базу в Docker volume `app-data`. Она сохраняется после остановки контейнеров. Если заданы `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN`, оба сервиса используют Turso вместо локальной базы.

Для просмотра только фронтенда и API, без запуска бота, выполните `docker compose up --build api web`. В этом режиме токен MAX не нужен.

Полезные команды:

```powershell
docker compose logs -f api bot web
docker compose down
```

При запуске в foreground остановите Compose через `Ctrl+C`, затем выполните `docker compose down`. Данные в named volume сохраняются. Повторный запуск без пересборки: `docker compose up -d`; после изменения кода или конфигурации: `docker compose up --build -d`. `docker compose down --volumes` удаляет локальную базу и кэш зависимостей фронтенда без возможности восстановления.

### Сценарий проверки

1. Откройте `http://localhost:5173/?demo=1`. Ожидается главная «Твой баланс» и синтетический список задач.
2. Создайте задачу с названием, предметом, сроком и одним из четырёх приоритетов. Ожидается новая карточка со статусом «Новая».
3. Отметьте задачу завершённой. Ожидается экран отметки состояния; после сохранения статус и процент выполнения обновятся.
4. Откройте «Даты», добавьте заметку и удалите её кнопкой-корзиной. Ожидается, что заметка появляется, а после удаления исчезает из списка.
5. В «Задачах» измените название, срок или приоритет и сохраните. Ожидается обновлённая карточка; удаление требует подтверждения.
6. В demo включите общий доступ и проверьте совместный экран. Demo-данные синтетические; реальные пользователи видны в общей группе только после opt-in.
7. Чтобы проверить бота, запустите все сервисы с настоящим `MAX_BOT_TOKEN`, найдите `@t165_hakaton_max_bot` в MAX и отправьте `/start`. При первом контакте ожидается согласие; после «Да» бот спрашивает о напоминаниях, затем открывает меню.
8. Напишите боту неизвестное сообщение. Ожидается список команд и функций; кнопка мини-приложения появляется, если `WEBAPP_URL` задан корректным HTTPS URL.
9. Откройте [production mini-app](https://max-bot-sable.vercel.app/) через MAX. Ожидается проверка `initData`, загрузка профиля и задач; прямой запрос к защищённому API без `X-Max-Init-Data` должен вернуть `401`.
10. Для совместного режима используйте только тестовые данные. До включения показывается состав данных, доступных участникам: имя, название задачи, предмет, срок и статус.

### Ожидаемые ответы API

- `POST /api/auth/validate` с актуальным MAX `initData`: `200` и `{ "ok": true, "user": ... }`; с неверной/устаревшей подписью: `401`.
- `GET /api/me` без `X-Max-Init-Data`: `401` и JSON с полем `error`.
- `POST /api/tasks` с корректным названием и RFC3339 deadline: `201`, задача создаётся со статусом `new`.
- `PATCH /api/tasks/{id}` с допустимым новым статусом: `200`; недопустимый переход: `409`.
- `POST /api/moods` с `good`, `ok` или `bad`: `201`, запись появляется в недельном обзоре.
- `POST /api/group/sharing` с `{"enabled":true}` / `false`: `200`; после отказа задачи пользователя не входят в групповой список.
- В локальном checkout `POST /api/tasks/scan` возвращает черновик из имени файла без анализа изображения. Команда сообщает, что production OCR подключён через Vercel; эта интеграция пока не воспроизводится из локального исходника.

Demo-режим проверяет только интерфейс и локальную логику. Для проверки реальной авторизации, API и хранения нужен MAX test account и свежий `initData`; не помещайте `initData`, токены и пароли в Git или презентацию.

## Компоненты и порты

| Компонент | Технологии / версия | Порт | Назначение |
| --- | --- | ---: | --- |
| `web` | Node.js 24, React 19, TypeScript 6, Vite 8 | `5173` | Локальный интерфейс и прокси `/api` |
| `api` | Go 1.25 | `8080` | REST API и авторизация MAX |
| `bot` | Go 1.25 | нет входящего порта | MAX long polling и напоминания |
| SQLite | `modernc.org/sqlite` из `go.mod` | нет | Локальная база в Docker volume |
| MAX Bot API | `max-bot-api-client-go` из `go.mod` | исходящие HTTPS-запросы | Сообщения, callbacks и напоминания |
| Vercel Cron | сервис Vercel | внешний | Production-вызов `/api/cron` ежедневно по расписанию `0 9 * * *` |

Внешние интеграции: MAX Bot API и MAX Mini App; Turso — необязательное постоянное хранилище; Yandex SpeechKit — необязательное распознавание голосовых сообщений; Vercel Cron — production-планировщик напоминаний. Эти внешние сервисы не запускаются в Docker.

## Работа с тестовыми данными

- `?demo=1` загружает синтетические задачи, участников и настроение из `frontend/src/data.ts`. Они сохраняются только в `localStorage` данного браузера и не попадают в API или SQLite.
- Локальные API-данные создаются вручную через mini-app внутри MAX или защищённые API-запросы. Новая SQLite-база не содержит заранее подготовленных пользовательских записей.
- Для проверки MAX используйте отдельный тестовый аккаунт и свежий `initData`. Для проверки совместного доступа включайте группу только на тестовых данных.
- Не используйте реальные заметки о здоровье, пароли, токены или персональные данные в demo. Для полного удаления локальной БД удалите Compose volume командой `docker compose down --volumes`.

## Переменные окружения

Список переменных и пример файла находятся в [`.env.example`](.env.example). Основные настройки:

| Переменная | Назначение |
| --- | --- |
| `MAX_BOT_TOKEN` | Токен бота MAX; нужен боту и проверке `initData` |
| `PORT` | В шаблоне указан `8080`; текущий Go server слушает фиксированный порт `8080` |
| `DB_PATH` | Путь к локальной SQLite-базе; по умолчанию `bot.db` |
| `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN` | Подключение к общей постоянной базе Turso; задаются вместе |
| `WEBAPP_URL` | Публичный URL мини-приложения, используемый ботом |
| `MAX_INIT_DATA_MAX_AGE` | Допустимый возраст `initData` в секундах; по умолчанию `3600` |
| `YANDEX_SPEECHKIT_API_KEY`, `YANDEX_FOLDER_ID` | Включают распознавание голосовых сообщений; если не заданы, распознавание отключено |
| `CRON_SECRET` | Секрет для авторизации Vercel Cron |
| `VITE_API_BASE` | Prefix API для запуска Vite вне Docker; по умолчанию `/api` |
| `VITE_API_PROXY_TARGET` | Цель Vite proxy; в Compose задано `http://api:8080` |

Файл `frontend/.env.example` содержит frontend-настройки для запуска Vite на хосте. В Docker отдельный frontend env-файл не нужен: Compose задаёт `VITE_API_PROXY_TARGET` внутри контейнера.

Не добавляйте `.env`, токены и другие секреты в Git. Настройка общей базы и развёртывания описана в [документе по базе данных](docs/DATABASE_SETUP.md).

## Разработка и проверки

Команды Go выполняются из корня репозитория:

```powershell
go test ./...
go run ./cmd/tokencheck
```

Команды фронтенда выполняются из `frontend`:

```powershell
npm run lint
npm run build
```

`tokencheck` использует `MAX_BOT_TOKEN` из `.env` или системного окружения и не выводит сам токен.

## Зависимости

Docker Compose запускает Go API и бота из общего `Dockerfile` на Go `1.25`; frontend-контейнер использует Node `24` и зависимости, указанные в `frontend/package.json` (React `19`, TypeScript `6`, Vite `8`, MAX UI). Go-библиотеки и версии фиксируются в `go.mod` и `go.sum`. При запуске `web` команда контейнера устанавливает npm-зависимости перед стартом Vite.

## Данные и ограничения

Локальная SQLite-база хранится в volume `app-data`; в production для постоянных данных нужны `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN`. В базе сохраняются MAX user ID и имя, задачи, отметки настроения и заметки. Настроение и заметки доступны только владельцу через API. При добровольном включении общего доступа участники группы видят имя пользователя и его задачи (название, предмет, срок и статус); отключение доступа удаляет участие из группы. Используйте для проверки только тестовые данные, не реальные сведения о здоровье или личных обстоятельствах.

Фото в production Vercel, по информации команды, обрабатывается подключённым OCR API. В текущем локальном checkout `/api/tasks/scan` остаётся mock-обработчиком: он формирует черновик из имени файла и не анализирует изображение. Поэтому локальный Docker пока не воспроизводит production OCR; реализацию/вызов внешнего сервиса нужно синхронизировать с репозиторием. Советы по нагрузке и реакции бота на настроение фиксированные и не являются медицинской оценкой или заменой психолога.

## Развёртывание

Production-развёртывание использует [Vercel](https://max-bot-sable.vercel.app/): фронтенд собирается командой `npm run build`, API доступен через `/api`, webhook — через `/api/webhook`, cron-задача напоминаний — через `/api/cron`. Для сохранения данных между вызовами serverless-функций настройте в Vercel `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN`. Без Turso Vercel использует временное хранилище в `/tmp`, которое не подходит для постоянных пользовательских данных.

Для запуска бота вне Vercel задайте ему те же параметры Turso, что и проекту Vercel. Подробности, в том числе ограничения расписания cron, приведены в [инструкции по настройке базы](docs/DATABASE_SETUP.md).

## Голосовые сообщения

При наличии согласия пользователя бот может отправить аудио в Yandex SpeechKit для распознавания. Используются аудио OGG Opus и язык `ru-RU`. Нужны `YANDEX_SPEECHKIT_API_KEY` и `YANDEX_FOLDER_ID`; API-ключ должен принадлежать сервисному аккаунту с доступом к SpeechKit.
