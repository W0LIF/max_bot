# «Телескоп» (max_bot) — распределение задач на 3 разработчика

Документ описывает 4 этапа: **1 — перенос дизайна**, **2 — REST API поверх Go-стора**,
**3 — бот ⇄ приложение**, **4 — инфраструктура и деплой**. Цель этапов 2–4: мини-приложение
и чат-бот MAX работают как единое целое, данные не теряются при перезапуске.

Правила разбиения (чтобы задачи не пересекались):

- **У каждой задачи один исполнитель.** Совместных задач нет; там, где нужна сверка,
  в описании указано, кто пишет код, а кто только ревьюит.
- **У каждого каталога один владелец** (таблица «Карта владения» внизу). Если задаче нужно
  трогать чужой файл — она либо переносится владельцу, либо файлом явно передаётся.
- **Сначала контракт, потом параллель.** Понедельник недели 1 — заморозка API-контракта
  и констант; до этого фронт и бэк пишут по черновику и не коммитят одну и ту же сущность.

## Текущее состояние (актуально на 29.09.2026)

### Готово
- **Фронтенд**: дизайн-система «Телескоп» (палитра, Manrope, UI-кит в `frontend/src/ui/`,
  стили в `frontend/src/styles/`), 18 экранов (`frontend/src/screens/`), навигация по стеку
  (`nav.tsx`), мок-стор с `localStorage` (`store.tsx`). `npm run build` и `npm run lint` проходят.
- **Бэкенд**: бот на long-polling (`cmd/bot/main.go`), FSM-диалоги добавления/редактирования/
  удаления/закрытия задач, кнопки меню (`pkg/bot/menu.go`), mood-колбэки, SQLite + memory
  стор (`pkg/storage`), планировщик напоминаний (`pkg/reminders`), валидация initData
  (`pkg/bot/validator.go`), webhook-хендлер (`pkg/bot/handlers.go`).

### Не готово (корень задач этапов 2–4)
- Фронтенд и бэкенд **не связаны**: приложение не делает ни одного запроса, все данные —
  моки из `store.tsx`.
- **Нет REST-API для мини-приложения**: интерфейс `storage.Store` есть, HTTP-поверх — нет.
- **Персистентность в serverless-пути сломана**: `HandleWebhook` каждый запрос создаёт
  `storage.NewMemoryStore()` (`pkg/bot/handlers.go:313`).
- **Напоминания не отправляются**: `cmd/bot/main.go:62` создаёт канал `remindersOut` и
  запускает шедулер, но никто из канала не читает — `Send` не вызывается ни разу.
- Из бота **нельзя открыть мини-приложение** одной кнопкой.
- **Расхождение моделей данных**: фронт (`frontend/src/data.ts:4-5`) знает 5 статусов
  (`overdue`, `frozen`) и 3 приоритета, БД — 3 статуса (`pkg/storage/task.go:11-13`) и
  два булевых флага `urgent`/`important`.
- **Валидатор initData не отдаёт пользователя**: `ValidateInitData` (`pkg/bot/validator.go:34`)
  возвращает только `bool`; `user_id` для API взять неоткуда.
- Распознавание по фото (экран 8) — только UI, OCR-сервиса нет.

### F4 — `types.ts`: единый источник типов (неделя 1)
**Файлы:** новый `frontend/src/types.ts`, `data.ts` (только моки), `store.tsx` (импорты).
Вынести `Task`, `TaskStatus`, `Priority`, `MoodEntry`, `Note`, `Member`, `Settings` из `data.ts`
в `types.ts`, оставив в `data.ts` только мок-данные (`INITIAL_TASKS`, `MOOD_HISTORY`, …).

**Обязательное выравнивание с БД (согласовано с Разрабом 3 в понедельник недели 1):**
- `TaskStatus` = `'new' | 'in_progress' | 'done'` — ровно как `storage.TaskStatus`
  (`pkg/storage/task.go:11-13`). Значения `overdue` и `frozen` **удалить**: `overdue` — это
  вычисляемое свойство (`deadline < today && status !== 'done'`), отдельный статус «на паузе»
  в MVP не входит. `STATUS_META` (`data.ts:54`) оставить с тремя ключами, бейдж «Просрочено»
  рисовать по вычисленному флагу.
- `Priority` **не приходит с сервера**: сервер хранит `urgent: boolean` и `important: boolean`.
  Фронт выводит `Priority` деривативно: `important && urgent → 'urgent'`, `important → 'important'`,
  `urgent → 'urgent'`, иначе `'later'`. Это упрощает `PRIORITY_META` до трёх записей, которые
  останутся верными.
- ID задач с сервера — числа (`int64`), поэтому `Task.id: string | number`, а сравнения
  приводить через `String(id)`; сейчас в `store.tsx` id вида `t1712345` — при переходе на API
  это ломает `toggleTask`.
- `subject` — обязательное поле (`data.ts:10`), приходит с сервера после B3.

**Готово, когда:** ни один экран не импортирует типы из `data.ts`; `npx tsc -b` зелёный.

# Этап 2 — Данные: REST API поверх Go-стора (Разраб 2)

**Заморозка контракта — понедельник недели 1, Разраб 3.** До заморозки Разраб 1 пишет `api.ts`
по черновику ниже и синхронизирует в конце дня 1.

Авторизация: все эндпоинты, кроме `POST /api/auth/validate` и `POST /api/webhook`, требуют
заголовок **`X-Max-Init-Data`**. Сервер проверяет его через `pkg/bot.ValidateInitData` и берёт
`user_id` оттуда. Локально API поднимает `go run ./cmd/server` (порт 8080), Vite проксирует
на него `/api` — `frontend/vite.config.ts:7-12`.

## Контракт API

```
POST   /api/auth/validate   { initData }                      -> 200 { ok, user{id,name} }
                                                       | 401 { error }   // без заголовка, initData в теле
GET    /api/me                                                  -> { id, name, consent, onboarded, reminders_on }
GET    /api/tasks            ?status=&limit=                   -> [Task]
POST   /api/tasks            { title, subject, deadline, urgent, important } -> Task
PATCH  /api/tasks/{id}       { title?, subject?, deadline?, urgent?, important?, status? } -> Task
DELETE /api/tasks/{id}                                          -> 204
GET    /api/moods            ?days=7                            -> [MoodEntry]
POST   /api/moods            { mood: good|ok|bad, note? }        -> MoodEntry
GET    /api/notes                                                 -> [Note]
POST   /api/notes            { text, allDay, start, end }        -> Note
DELETE /api/notes/{id}                                          -> 204
GET    /api/group/members                                       -> [Member]
GET    /api/group/tasks                                         -> [Task]
POST   /api/tasks/scan       multipart: photo                   -> { title, subject, deadline }
POST   /api/feedback         { text }                            -> 200
POST   /api/webhook          (уже есть, апдейты от MAX)
```

**Соглашения по контракту:**

- `Task` = `storage.Task` + `subject` (миграция в B3). JSON: `id` (число), `user_id`,
  `title`, `subject`, `deadline` (RFC3339 UTC), `urgent`, `important`, `status`.
- `status` — только `new | in_progress | done`. Переходы проверяются существующим
  `Task.CanTransitionTo` (`pkg/storage/task.go:46`), недопустимый → `409`.
- `priority` в API **нет**: приоритет = `urgent` + `important` во входе, на фронте выводится
  в `Priority` (см. F4).
- `PATCH` частичный: меняем только переданные поля, читаем через `GetTask`, пишем
  `UpdateTask`.
- Даты — RFC3339; фронт конвертирует в локальную зону при отрисовке.
- Ошибки всегда `{"error": "<русский текст>"}` с кодами: `400` валидация, `401` плохой
  initData, `403` чужой ресурс, `404` не найдено, `409` конфликт перехода.
- `user.name`: приходит из initData (поле `user.first_name`), при отсутствии — «Студент».
  Бэкенд не ходит в MAX за профилем.
- CORS: `Access-Control-Allow-Origin: *` уже прописан в `HandleValidate`
  (`pkg/bot/handlers.go:326`) — тот же набор заголовков нужен на всех маршрутах, иначе
  локальная разработка через другой порт не заработает.

### B1 — Роутер и авторизация (неделя 1)
**Файлы:** `pkg/httpapi/router.go`, `pkg/httpapi/middleware.go`, `pkg/httpapi/ctx.go`,
`pkg/bot/validator.go` (добавление), `cmd/server/main.go` (регистрация).

- `httpapi.New(store storage.Store, notifier Notifier) http.Handler` — Go 1.25, маршруты
  через `ServeMux` с паттернами (`"GET /api/tasks"`, `"PATCH /api/tasks/{id}"`), Go 1.22+.
- Middleware `RequireInitData`: читает заголовок → `bot.ValidateInitData(raw, MAX_BOT_TOKEN,
  MAX_INIT_DATA_MAX_AGE)` → кладёт `user_id` в `context.Context`. На `ErrExpiredInitData` —
  `401` с отдельным текстом «Данные устарели, перезапустите приложение», на невалидной
  подписи — `401`.
- **Новая функция `bot.ParseInitData(raw string) (User, error)`** в `pkg/bot/validator.go`:
  парсит `url.ParseQuery`, достаёт `user.id`, `user.first_name`/`user.name`, проверяет, что
  значения встречаются ровно один раз. Рефакторинг: `validateInitData` начинает использовать
  её же, чтобы не было двух разборов формата.
- CORS-обёртка на все маршруты + обработчик `OPTIONS`.
- `cmd/server/main.go`: заменить два ручных `mux.HandleFunc` на
  `http.ListenAndServe(addr, httpapi.New(store, notifier))`, где `store` — тот же
  SQLite-стор, что и у бота (`storage.NewSQLiteStore(os.Getenv("DB_PATH"))`).
  Старый `/api/validate` остаётся рабочим для отладки, новый `/api/auth/validate` —
  в роутере.
- `Notifier` — интерфейс с одним методом `NotifyTaskCreated(ctx, userID, task)`; реализация
  в `pkg/bot` (M5). В B1 — заглушка-логгер, чтобы не было циклической зависимости
  `httpapi → bot → httpapi`.

**Готово, когда:** `curl` с валидным initData возвращает 200, без него — 401; старый
`cmd/server` поднимается одной командой.

### B2 — CRUD задач (неделя 1)
**Файлы:** `pkg/httpapi/tasks.go`, `pkg/bot/validator.go` (только если понадобится).
`GET/POST/PATCH/DELETE /api/tasks`. Ничего нового в `storage.Store` не нужно — хватает
`CreateTask`, `GetTasks`, `GetTask`, `UpdateTask`, `DeleteTask`, `SetTaskStatus`.

- `GET`: `status` фильтрует по статусу, `limit` (по умолчанию 100, максимум 500) режет;
  сортировка уже есть в `sortTasks` внутри `GetTasks`.
- `POST`: валидация `title` (1–200 символов, правило как в `onTaskTitle`,
  `pkg/bot/dialog_add.go:21`), `deadline` — RFC3339, `subject` — одно из значений
  (после B3; до B3 принимаем любую строку). Ответ 201 + созданный `Task`.
- `PATCH`: читаем `GetTask` → применяем только переданные поля → `UpdateTask`; если передан

- Доступ: `GetTask(ctx, userID, id)` уже фильтрует по владельцу, чужая задача → 404 (не 403,

## Риски

- **Хостинг/БД (I1)** — главный риск проекта: без решения до среды недели 1 часть работы
  Разраба 2 (B3, B6) придётся переделывать. Митигация: решение — первым пунктом недели 1.
- **OCR (B5)** — внешний сервис может быть недоступен; держим заглушку, приёмку это не
  блокирует (сценарий 6 проверяет путь «фото → форма», а не точность распознавания).
- **Расхождение формулировок** статусов и приоритетов в боте и приложении — лечится
  заморозкой контракта в понедельник и сверкой M4, а не правками на ходу.
- **Дрейф моделей данных** (5 статусов / 3 приоритета на фронте против 3 статусов и двух
  флагов в БД) — главный источник багов этапа 2; закрывается в F4 до того, как фронт
  начнёт читать API.
- **Serverless-состояние** — пока I1 не решён, `HandleWebhook` на Vercel продолжает терять
  данные; это известное и принятое ограничение, а не сюрприз на приёмке.
